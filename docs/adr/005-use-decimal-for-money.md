# ADR-005: 金額計算に Decimal を使用する

## ステータス

採用

## 日付

2026-07-16

## 背景

Flowance Phase1 では、時間単価契約、月額精算幅契約、月額固定契約、成果報酬契約を扱い、稼働実績や予定に基づいて月次精算を計算する。

金額計算では、消費税、源泉徴収、控除、超過、合計額を扱うため、浮動小数点誤差を避ける必要がある。

要件定義、基本設計、DB 設計、契約・売上計算詳細設計では、Python の float を使用しない方針としている。

## 決定

金額計算には Decimal を使用する。

- Python では decimal.Decimal を使用する。
- Django では DecimalField または整数金額を使用する。
- PostgreSQL では numeric または bigint を使用する。
- JPY の最終保存金額は 1 円単位の整数を基本とする。
- float は金額計算に使用しない。
- 消費税は税率単位で 1 回だけ ROUND_DOWN する。
- 源泉徴収は ROUND_DOWN 固定とする。
- total_amount は丸め済みの税額・源泉徴収額を使って算出し、追加の二重丸めをしない。

## 理由

- float は 10 進小数を正確に表現できず、金額計算に不向きである。
- Decimal により、税額・源泉徴収・単価計算の丸めを明示的に制御できる。
- calculation_snapshot に計算根拠を残す際、再計算可能性と説明可能性を保てる。
- JPY は 1 円単位の整数保存と相性がよい。
- Phase2 の請求書・入金・分析へ拡張するときも、金額の整合性を保ちやすい。

## 影響

### 良い影響

- 金額計算の再現性が高くなる。
- 税額・源泉徴収の丸め方針を一貫できる。
- テストで期待値を明確に定義できる。
- 請求書・入金機能の追加時にも金額の土台を流用できる。

### 注意点

- Decimal と int の変換境界を明確にする必要がある。
- API レスポンスでは JPY 金額を整数として返す方針を統一する。
- DB の numeric / bigint の使い分けを設計書と実装で揃える。
- 消費税丸めの組織別設定は Phase2 以降の拡張として残す。

## 採用しない選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| float | 丸め誤差が発生し、税額・源泉徴収・合計額に不整合が出る |
| すべて文字列で金額を扱う | 計算処理が煩雑になり、型安全性が下がる |
| フロントエンドで金額計算する | 業務ルールをバックエンドへ集約する方針と合わない |

## Phase1 未対応事項

- 外貨対応
- 複数通貨
- 組織別の消費税丸め方式設定
- 源泉徴収対象を税込金額にする契約別設定
- 請求書明細単位の複数税率計算
- 返金、相殺、負の精算
