# Flowance サービス志向 UI デザイン方針

## 1. 目的

Flowance の UI は、単なる SaaS 管理画面やシステム管理画面ではなく、フリーランスや小規模チームが「案件、稼働、売上、精算を迷わず整えられるサービス」として設計する。

Phase1 では契約、予定、稼働実績、月次精算の正確性が重要だが、画面上では内部ドメインや API 構造をそのまま見せすぎない。ユーザーが今日やるべきこと、確認すべきこと、次に進められることを中心に体験を組み立てる。

## 2. デザイン判断

### 2.1 採用する方向性

- 業務データ中心ではなく、ユーザーの仕事の流れ中心にする。
- CRUD の入口を並べるのではなく、「今日の予定」「未入力の実績」「今月の売上見込み」「精算前の確認」など、次の行動を前面に出す。
- 管理者向けの硬い語彙を避け、ユーザーが実務で使う言葉に置き換える。
- 契約や精算の信頼感は保ちつつ、アイコン、色、進捗、空状態、確認メッセージでサービスらしい温度感を出す。
- 状態やエラーはコード名ではなく、原因と次にできることを表示する。

### 2.2 避ける方向性

- KPI カード、テーブル、サイドナビだけで構成された汎用 SaaS ダッシュボード。
- API リソース名やドメイン名をそのまま画面名にする構成。
- 「登録」「更新」「削除」「再計算」など、システム操作だけが目立つ UI。
- 装飾的なグラデーションや抽象的なカードを増やして、肝心の作業が遠くなる見せ方。
- 請求、入金、分析など Phase1 対象外の機能を主導線に見せること。

## 3. 情報設計

### 3.1 第一階層

| 表示名 | 目的 | 主な対象 |
| --- | --- | --- |
| ホーム | 今日の作業、未入力、売上見込み、精算準備をまとめて確認する | 予定、実績、精算 |
| カレンダー | 週次予定と個別予定、実績を日付軸で扱う | Scheduling, Work Records |
| 案件 | クライアント、案件、料金条件、メンバーを扱う | Clients, Projects, Contracts |
| 売上確認 | 月ごとの売上見込み、精算計算、確定を扱う | Settlements |
| 設定 | 組織、メンバー、アカウントを扱う | Organizations, Accounts |

Phase1 では「請求書」「入金」「分析」は第一階層に出さない。必要な場合は売上確認内の将来拡張として、無効状態や予告表示に留める。

### 3.2 ホームで答える問い

ホームは次の問いに 10 秒以内で答えられる構成にする。

- 今日どの案件で作業するか。
- 入力し忘れている実績はあるか。
- 今月いくらになりそうか。
- 精算前に確認が必要な案件はどれか。
- 今すぐ押せる主要アクションは何か。

## 4. 画面別方針

### 4.1 ホーム

ホームは「ダッシュボード」ではなく「作業開始地点」とする。

優先表示:

- 今日の予定と開始できる作業。
- 未入力または下書きの実績。
- 今月の売上見込み。
- 精算できる案件。
- 契約未設定、対象契約なし、複数契約該当などの注意。

推奨アクション:

- 実績を入力する。
- 今日の予定を追加する。
- 今月の売上を確認する。
- 精算内容を確定する。

### 4.2 案件

案件画面は「案件台帳」ではなく「仕事ごとの状況確認」として設計する。

案件カードまたは一覧には、案件名だけでなく、クライアント、今月の予定時間、実績時間、売上見込み、契約状態、次の確認事項を表示する。

契約は「契約管理」ではなく「料金条件」と表示する。時間単価、月額固定、月額精算幅、成果報酬は、入力項目の羅列ではなく、選択した契約種別に応じたフォームへ段階的に切り替える。

### 4.3 カレンダー

カレンダーは予定と実績の差分を把握できる画面にする。

- 予定は淡い表示、実績は明確な表示にする。
- 実績化済みの予定は完了状態を視覚的に示す。
- 案件アイコンと色を使い、どの仕事かを瞬時に識別できるようにする。
- 予定から実績入力へ自然に進める導線を持つ。

### 4.4 売上確認

売上確認は会計システムのような精算テーブルではなく、「今月の金額を安心して確定する」画面にする。

表示順:

1. 今月の見込み合計。
2. 案件ごとの金額と状態。
3. 計算根拠の要約。
4. 税額、源泉徴収、控除、超過の詳細。
5. 確定アクション。

計算根拠は常に追えるようにするが、初期表示では要点だけを見せる。詳細は展開で確認できるようにする。

## 5. 用語方針

| 内部用語 | 画面表示の推奨 |
| --- | --- |
| Contract | 料金条件 |
| ProjectContract | 案件の料金条件 |
| WorkRecord | 稼働実績 |
| WorkSchedule | 予定 |
| MonthlyProjectSettlement | 月ごとの売上確認 |
| Calculate settlement | 売上を計算 |
| Recalculate settlement | 最新の実績で更新 |
| Finalize settlement | この内容で確定 |
| CALCULATED | 確認中 |
| FINALIZED | 確定済み |
| INVALID_CONTRACT_CONDITION | 料金条件を確認してください |
| SETTLEMENT_TARGET_NOT_FOUND | この月に使える料金条件がありません |
| MULTIPLE_CONTRACTS_IN_MONTH | この月に複数の料金条件が重なっています |

## 6. ビジュアル方針

### 6.1 全体トーン

- 信頼感があり、静かで、少し親しみがある。
- 金額や契約を扱うため、過度にポップにしない。
- 汎用 SaaS の青白い管理画面に寄せすぎず、案件アイコン、状態色、進捗、余白でサービスらしさを作る。

### 6.2 色

- ベースは白またはごく淡いニュートラル。
- 主要アクションは 1 色に統一する。
- 案件やクライアントの識別色は、画面全体のテーマ色ではなく局所的に使う。
- 警告、成功、未完了、確定済みなどの意味色を明確に分ける。

### 6.3 コンポーネント

- カードは個別の案件、予定、注意事項など、まとまりを示す場合に限定する。
- 画面全体をカードだらけにしない。
- 主要アクションは大きく、視線の流れに沿って配置する。
- 補助操作はアイコンボタンやメニューへ整理する。
- 空状態では、何がないかだけでなく、次にできる行動を表示する。

## 7. Phase1 実装時の優先順位

1. ホームの「今日やること」と「今月の売上見込み」を設計する。
2. 案件詳細に「料金条件」「予定」「実績」「売上確認」への導線をまとめる。
3. 売上確認画面で、計算結果と根拠を安心して確認できる構造にする。
4. エラー表示を、コード中心からユーザー行動中心へ置き換える。
5. 空状態、未設定状態、確定済み状態の文言と見た目を整える。

## 8. 受け入れ基準

- 初回ログイン後、ユーザーが次に何をすればよいか分かる。
- 契約や精算の内部用語を知らなくても、料金条件と売上確認の意味が分かる。
- Phase1 対象外の請求、入金、分析が主導線に出ていない。
- 金額の計算根拠を必要なときに確認できる。
- 画面が CRUD リソース一覧ではなく、仕事の流れとして理解できる。
