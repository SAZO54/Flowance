flowance-web と E2E の実態

重大

層をまたぐテストが 0 件 — infrastructure が一度も import されていない

テスト 8 ファイルのいずれからも @/infrastructure への import が無く、 vi.mock / global.fetch / vi.stubGlobal の使用も 0 件である。 つまりフロントエンドが Django に対して実際にどんな HTTP リクエストを送るかを検証する手段が、 コードベース上に一つも存在しない。

未検証のまま残っている apiClient.ts（157 行）の責務： 全リクエストの credentials: 'include'、 unsafe メソッド時の csrftoken Cookie 読み取りと X-CSRFToken 付与、 401 時のリフレッシュ single-flight と 1 回だけの再送、 payload.code ?? HTTP_${status} のフォールバック、 traceId の 3 段解決、 そして toApiError が副作用としてグローバル CustomEvent を発火すること。

AGENTS.md に則った結合テストのすすめ

4.1 条項をテスト方針に翻訳する

AGENTS.md §11 Use PostgreSQL constraints for data integrity that must not be bypassed.

→「バイパスされてはならない」制約は、アプリ層を迂回して DB に直接書き込むテストでしか検証できない。TransactionTestCase の導入が前提になる。

AGENTS.md §12 Tasks must be idempotent where retry is possible. / Preserve traceId across API and Celery task boundaries.

→ 現在 retry が未実装で traceId も渡っていない。テストを書く前に実装が必要な項目として切り分ける。

AGENTS.md §12 PostgreSQL background_tasks is the business-visible task state source.

→ Celery の内部状態ではなく background_tasks を見る設計。.delay() 経由で呼んでも状態が正しく遷移することを検証すべき箇所。

AGENTS.md §9 Put API communication in infrastructure adapters. / Put use-case orchestration in application layer.

→ 層が正しく分かれているからこそ、その接続点は明示的に検証しないと誰も守らない。Composition の配線テストがその役割。

AGENTS.md §13 Run the smallest meaningful verification that matches the risk of the change.

→ 結合テストは遅い。pytest.ini のマーカーを実際に使い、-m integration で選択実行できるようにする。

test-design.md E2E は Phase1 受入条件に直結する主要フローへ絞る。

→ E2E を増やすのではなく、既にある 1 本を通すことが目標。そのための API フィクスチャ整備が本丸。

4.3 DB 制約を実際に踏むテストを追加する

契約期間重複の ExclusionConstraint は AGENTS.md §6.3 が 「Enforce overlap with both Application validation and PostgreSQL exclusion constraint」と定める二重防御である。 現状はアプリ層の検証しか通っておらず、DB 側の防御が生きているか誰も知らない。 マイグレーションのミスで制約が落ちても気付けない。

TransactionTestCase が必要な理由。 通常の TestCase は各テストをトランザクションで包んでロールバックするため、 COMMIT 時に評価される制約や transaction.on_commit が発火しない。 現に既存テストは captureOnCommitCallbacks(execute=True) で on_commit を人工的に実行している。 DB 制約・並行トランザクション・select_for_update を検証するなら TransactionTestCase が前提になる。実行は遅くなるので @pytest.mark.integration を付けて選択実行できるようにする。

4.4 Celery を .delay() 経由で通す

CELERY_TASK_ALWAYS_EAGER = True は既に設定済みなので、 .delay のモックを外すだけで dispatch 層を通せるようになる。 これでサービス → .delay() → タスク本体 → background_tasks 更新までが一本の結合テストになる。

既存テストの変更方針
# 現状: apps/clients/tests/presentation/test_api.py:115
@patch("apps.clients.application.services.process_client_icon.delay")
def test_icon_upload_processing_and_delete(self, delay):
    ...
    delay.assert_called_once()          # ここで経路が切れている
    process_client_icon.run(task_id)    # 手動で本体を呼び直している

# 変更後: モックを外し EAGER に任せる
def test_icon_upload_processing_and_delete(self):
    with self.captureOnCommitCallbacks(execute=True):
        response = self.client.post(..., format="multipart", **self.headers)
    # .delay() → EAGER 実行 → タスク本体 → BackgroundTask 更新まで通る
    self.assertEqual(BackgroundTask.objects.get(...).status, "SUCCEEDED")
