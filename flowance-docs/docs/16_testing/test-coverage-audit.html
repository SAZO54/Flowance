§1

検出事項

スイートを実際に実行して判明した、テストを増やす前に塞ぐべき穴。

重大

apps/settings のテスト 11 件が丸ごと実行されていない

apps/settings/tests/ と apps/settings/tests/presentation/ に __init__.py が存在しない。 他の 11 アプリにはすべて配置されているため、settings だけが Django のテストディスカバリからパッケージとして認識されず、 エラーも警告も出さずに沈黙している。 

$ docker exec flowance-api-api-1 python manage.py test apps.settings \
    --settings=config.settings.test
Found 0 test(s).
NO TESTS RAN

grep 上のテストメソッドは 71 件あるが、ランナーが検出するのは 60 件。差分 11 件が settings の test_api.py（8 件）と test_validation.py（3 件）にちょうど一致する。 カバレッジ最下位の apps/settings/application/service.py 33%、 apps/settings/presentation/views.py 48% はこれが原因。

結果として、OWNER 以外による組織情報・事業者情報の更新拒否、 version 競合時に他セクションもロールバックされること、 Cookie 認証時の CSRF 必須、email が更新不可であること といった、AGENTS.md §6.2・§8 に直結する検証がすべて未実行のまま出荷されている。

対処：以下 2 ファイルを空で追加するだけで 11 件が復活する。
apps/settings/tests/__init__.py / apps/settings/tests/presentation/__init__.py
復活後にテストが通ることの確認まで含めて 1 コミット。
重大

既存テストが 1 件失敗している — 週次予定と個別予定で業務ルールの境界が食い違う

FAIL: test_weekly_schedule_crud_bulk_and_validation
  File "apps/schedules/tests/presentation/test_api.py", line 114
    self.assertEqual(invalid.status_code, 422)
AssertionError: 201 != 422

10:00–18:00（実働 480 分）に対し breakMinutes=480 を指定すると、 実働 0 分の週次予定が作成できてしまう。原因は同一ファイル内の比較演算子の不一致。 

# apps/schedules/domain/generation.py

def validate_weekly_schedule(...):
    ...
    if break_minutes < 0 or break_minutes > duration:    # L70  休憩 == 実働 を許容
        raise InvalidBreakMinutesError()

def validate_work_schedule(...):
    ...
    if break_minutes < 0 or break_minutes >= duration:   # L85  休憩 == 実働 を拒否
        raise InvalidBreakMinutesError()

apps/schedules/presentation/serializers.py:47 も > 側であり、 週次予定（テンプレート）と個別予定（生成後の実体）で同じ業務ルールの境界が異なる。 テンプレートが実働 0 分の予定を量産できる一方、生成された個別予定は同じ値を拒否するため、整合性が取れていない。

対処：まず flowance-docs/docs/14_schedule-generation に境界仕様（休憩 == 実働 を許すか）を明記する。 現状この文書に breakMinutes の記述はなく、どちらが正か仕様上決まっていないため、 実装だけを直すと再発する。仕様確定後に両関数の演算子を揃え、境界値テストを apps/schedules/tests/domain/ に SimpleTestCase として追加する。
構造

Application 層のテストがゼロ — テストピラミッドが逆立ちしている

docs/16_testing/test-design.md の基本方針は 「業務ルールは Domain / Application のテストで重点的に検証する」だが、実態は完全に逆である。 schedules/application/work_service.py（431 行）、 settlements/application/service.py（433 行）、 projects/application/services.py（320 行）、 work_records/application/services.py（316 行）は、 いずれも HTTP 経由でしか実行されたことがない。

カバレッジ 84〜92% という数値は「API テストがたまたま通過した行」であり、 ユースケース単位の異常系・権限分岐・トランザクション境界を意図して検証した結果ではない。

基盤

pytest が実行不能／テストユーティリティが未使用

requirements.txt には pytest==9.1.1 / pytest-django==4.12.0 / pytest-cov==7.1.0 / factory_boy / Faker / freezegun が入っているが、 pytest.ini / pyproject.toml / setup.cfg / conftest.py が リポジトリのどこにも存在しない。DJANGO_SETTINGS_MODULE が解決できず pytest は起動できない。

実際には manage.py test（unittest）で動いており、AGENTS.md §3.2・§13 の「pytest」という記述と乖離している。 また factory_boy / Faker / freezegun のテストコードからの利用は 0 件で、 各 setUp に組織・ユーザー・案件・契約の生成が手書きで重複している。

配置

純粋な計算テストが APITestCase で書かれている

settlements/tests/presentation/test_api.py::SettlementCalculationTests と work_records/tests/presentation/test_api.py::WorkRecordCalculationTests は、 金額計算・丸め規則という純粋なドメイン検証にもかかわらず APITestCase で書かれており、 DB と HTTP スタックを毎回起動している。本来 tests/domain/ の SimpleTestCase に置くべきもので、 境界値を増やすほど遅くなりテストが書かれなくなる構造になっている。

§5

AGENTS.md に則った単体テストのすすめ

ここからは調査結果ではなく提案である。AGENTS.md の各条項を、そのままテストの置き場所と書き方に落とし込む。

5.1 まず、AGENTS.md の条項をテスト方針に翻訳する

AGENTS.md §6 Domain code must not depend on Django, DRF, ORM, Redis, Celery, Pillow, Storage, or HTTP.

→ Domain のテストは SimpleTestCase（DB なし）で書ける。書けないなら依存方向が壊れているという設計チェックとして機能する。

AGENTS.md §6 Business rules belong primarily in Domain or Application layers.

→ 業務ルールの境界値は Domain テストで、権限とトランザクションは Application テストで網羅する。API テストで境界値を潰さない。

AGENTS.md §8 401 / 403 / 404 / 409 / 422 の使い分け、ErrorResponse 統一

→ Presentation テストの守備範囲を「ステータスコード・エラー形状・Cookie・CSRF」に限定し、金額や日付の正しさは検証しない。

AGENTS.md §9 Keep domain concepts independent from React, Next.js, TanStack Query, ... and browser APIs.

→ flowance-web も同じ判定が使える。src/domain/ と src/application/ は environment: node でテストできるはず。

AGENTS.md §11 Use version columns for optimistic locking / exclusion constraint for contract overlap

→ DB 制約に依存する検証は TestCase（PostgreSQL 実接続）で。SQLite 代替は使わない。

AGENTS.md §13 Before handing off code changes, run the smallest meaningful verification that matches the risk of the change.

→ 「Domain だけ 1 秒で回る」状態を作ることが前提条件。現状は全件 DB 起動のため、この条項が実行不可能になっている。

5.4 Domain テストの書き方 — 精算計算を例に

settlements/domain/calculation.py は Django に一切依存していない（Decimal と 自前の DomainValidationError のみ）。つまり AGENTS.md §6 の依存方向は守られており、 DB もフィクスチャもなしにテストできる。現状これが API テスト経由でしか検証されていないのが機会損失である。

apps/settlements/tests/domain/test_calculation.py（新規）
from decimal import Decimal
import pytest

from apps.settlements.domain.calculation import (
    InvalidContractConfigurationError,
    NegativeSettlementTotalError,
    SettlementContractTerms,
    calculate_amounts,
)

pytestmark = pytest.mark.domain


def terms(**overrides) -> SettlementContractTerms:
    base = dict(
        contract_type="HOURLY", hourly_rate=5000, monthly_rate=None,
        base_minutes=None, deduction_rate=None, overtime_rate=None,
        performance_amount=None,
        tax_rate=Decimal("10"), withholding_tax_rate=Decimal("10.21"),
    )
    return SettlementContractTerms(**{**base, **overrides})


class TestHourly:
    def test_端数は切り捨てられる(self):
        # 10 分 x 5000 円/h = 833.33... -> ROUND_FLOOR で 833
        result = calculate_amounts(contract_terms=terms(), target_minutes=10)
        assert result.base_amount == 833

    def test_時間単価が無いと契約設定エラー(self):
        with pytest.raises(InvalidContractConfigurationError):
            calculate_amounts(contract_terms=terms(hourly_rate=None), target_minutes=60)


class TestMonthlyRange:
    """AGENTS.md §6.4「base_minutes 差分を控除・超過計算の基礎とする」の検証。"""

    def spec(self, **o):
        return terms(contract_type="MONTHLY_RANGE", hourly_rate=None,
                     monthly_rate=500_000, base_minutes=9600,
                     deduction_rate=3000, overtime_rate=3500, **o)

    def test_基準時間ちょうどなら控除も超過も発生しない(self):
        result = calculate_amounts(contract_terms=self.spec(), target_minutes=9600)
        assert (result.deduction_amount, result.overtime_amount) == (0, 0)
        assert result.base_amount == 500_000

    def test_不足分は控除され超過分は加算される(self):
        under = calculate_amounts(contract_terms=self.spec(), target_minutes=9000)
        over = calculate_amounts(contract_terms=self.spec(), target_minutes=10200)
        assert under.deduction_amount == 30_000   # 600分 x 3000/60
        assert over.overtime_amount == 35_000     # 600分 x 3500/60

    def test_控除が月額を上回ると負値エラー(self):
        with pytest.raises(NegativeSettlementTotalError):
            calculate_amounts(contract_terms=self.spec(monthly_rate=1000),
                              target_minutes=0)


@pytest.mark.parametrize("contract_type,field", [
    ("MONTHLY_FIXED", "monthly_rate"),
    ("PERFORMANCE", "performance_amount"),
])
def test_必須項目が欠けると契約設定エラー(contract_type, field):
    with pytest.raises(InvalidContractConfigurationError):
        calculate_amounts(
            contract_terms=terms(contract_type=contract_type, hourly_rate=None,
                                 **{field: None}),
            target_minutes=9600,
        )


def test_源泉徴収は税抜額に対して計算され合計から差し引かれる():
    # AGENTS.md §6.4: 消費税と源泉徴収の計算順序を固定する
    result = calculate_amounts(
        contract_terms=terms(contract_type="MONTHLY_FIXED", hourly_rate=None,
                             monthly_rate=100_000),
        target_minutes=0,
    )
    assert result.tax_amount == 10_000          # 100,000 x 10%
    assert result.withholding_amount == 10_210  # 100,000 x 10.21%（税抜基準）
    assert result.total_amount == 99_790

同じ形で contracts/tests/domain/test_validation.py（4 種契約の必須条件、期間重複の境界日）と schedules/tests/domain/test_generation.py（100 日境界、手動上書き保護、day_of_week の 0=日曜、 §1 で見つかった breakMinutes の境界）を追加する。 いずれも DB 不要のため、この 3 ファイルだけなら 1 秒未満で回る。

5.5 Application テストの書き方 — 依存をスタブに差し替える

Application 層のテストがゼロである最大の理由は、テストするために組織・ユーザー・案件・契約を毎回 DB に作る必要があるためだと推測される。 AGENTS.md §6「Database access belongs behind repository or infrastructure boundaries where practical」に沿って、 まずテストしたいユースケース 1 つに限定して依存を引数化するのが最小の一歩である。

apps/settlements/tests/application/test_finalize.py（新規・方針例）
import pytest

pytestmark = pytest.mark.application


class FakeIdempotencyStore:
    """Idempotency-Key の保存先を差し替える。DB も Redis も起動しない。"""

    def __init__(self):
        self.saved = {}

    def find(self, *, organization_id, key):
        return self.saved.get((organization_id, key))

    def save(self, *, organization_id, key, request_hash, response):
        self.saved[(organization_id, key)] = (request_hash, response)
